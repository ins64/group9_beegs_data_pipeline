# 10 · What did not work, and what we would do differently

> Criterion C8 asks for explicit limitations. This page lists the real problems we hit while building and running the pipeline, what each one taught us, and what we changed. Every item is backed by a commit or a GitHub Actions run in the repository.

## 1. Problems we actually hit (and what we changed)

| # | What happened | Root cause | What we changed | Lesson |
|---|---|---|---|---|
| 1 | **We dropped Google Cloud** mid-project (BigQuery/GCS were planned first). | Two clouds meant two IAM models, two bills and two sets of secrets for a team of 4 in a few days. The Snowflake account already runs on Google Cloud. | Snowflake only: the internal stage replaces the bucket and GitHub Actions replaces Cloud Run. Documented in docs/03 §5. | **Fewer moving parts beats a "complete" diagram.** One cloud, one IAM, one bill. |
| 2 | **The Open-Meteo archive API was down during our initial load** (HTTP 503, then timeouts). The whole backfill failed although 6 other sources were fine. | The extract job ran the sources one after the other and stopped at the first exception. | Each external source is now **isolated**: a failure is logged, the other sources and the internal files still land, and the run is marked failed so the outage is visible. Watermarks make the next run catch up. (commit "isolate each external API") | **Design for partial failure.** One external dependency must never block the others. This is incident INC-004, which we first only "documented" and then lived for real. |
| 3 | Asking Open-Meteo for 6 years of history in one call **timed out**. | The API is not designed for one huge request. | The backfill is cut into **one request per year and per apiary**. | Backfills need chunking and longer timeouts than daily runs. |
| 4 | The first run of the extract job crashed on `GET` of a **watermark file that did not exist yet**. | The "first run" was never tested against the real stage (only locally). | `LIST` before `GET`; no watermark = full history. | **Test the empty state**, not only the steady state. |
| 5 | The **backtest** (`--vars as_of_date`) ran without error but gave **today's** numbers. | dbt on Snowflake splits `ARGS` like a shell: without quotes, the YAML of `--vars` was cut in two and the variable was silently ignored. | The vars are passed as one quoted token (`$$ ... --vars '{as_of_date: 2026-03-30}' $$`). GOLD now holds two decision dates (2026-03-30 and 2026-11-01), and the backtest on Snowflake flags TILLEUL (W15) and COLZA (W18), as the local run did. | **A green run is not a proof.** Check the output (rows per decision date), not only the exit code. |
| 6 | **Future grants / managed access** failed in OpenTofu. | They need the account-wide `MANAGE GRANTS` privilege, which we did not want to give to the CI user. | dbt grants SELECT on each GOLD table when it builds it (post-hook). | Least privilege has a price: a little more code, much less risk. |
| 7 | The **ACCOUNTADMIN bootstrap** could not be automated. | Creating roles, users, the resource monitor and the e-mail integration needs ACCOUNTADMIN, which CI must never have. | One short manual script (`00_bootstrap_accountadmin.sql`), run once by a human, documented in the runbook. Everything else is CI. | Accept one documented manual step rather than an over-privileged robot. |
| 8 | **Snowflake features unavailable on a trial account**: external network access (calling APIs from Snowflake) and the Snowflake MCP connector. | Trial limitations. | The API calls run in our container on GitHub Actions and land raw files in the stage. | Check the account's limits before designing around a feature. |
| 9 | **Snowpipe auto-ingest is impossible on an internal stage** (no cloud event). | Auto-ingest needs an external bucket with notifications. | The producer triggers the pipe itself (`ALTER PIPE … REFRESH PREFIX`) right after its upload. | Same latency, no bucket to manage. |
| 10 | Locally, **DuckDB ran out of memory** on JSON arrays, and some SQL behaved differently from Snowflake (`regexp_replace`). | The local engine is not Snowflake. | Cross-database macros (`macros/cross_db.sql`) and window functions instead of correlated subqueries. | The local twin is very useful (free, 2 min) but every model must also be run on the real target. |
| 11 | Our **daily task graph had never succeeded** on Snowflake: the root task failed on its first statement. We only saw it when the incident drill checked the run log. | `SYSTEM$SET_RETURN_VALUE` only accepts a constant; we passed it a computed date. | Each task computes the run date itself from the graph's scheduled time (inside a small SQL script block). | Tested locally ≠ tested on the platform: the orchestration layer has to be run for real, not only the SQL it calls. |
| 12 | The finalizer logged **every** run as `FAILED`, even green ones. | `LISTAGG` over zero rows returns an empty string, not `NULL`. | `NULLIF(LISTAGG(...), '')`. | Same lesson: assert the result of a success, not only of a failure. |
| 13 | The broken lab file was uploaded but **never loaded**. | `ALTER PIPE … REFRESH PREFIX` is relative to the pipe's own folder (`dt=…/`), not to the stage root (`lab_results/dt=…/`). The extract job had it right, the incident script had it wrong. | Fixed in the incident script, the drill and the demo. The `incident-drill` workflow now **asserts** the expected outcome (FAILED run + untouched GOLD, then SUCCESS + refreshed GOLD) and fails otherwise. | An incident test must check its own preconditions (here: the bad file is really in bronze). |
| 14 | The **cockpit crashed** in its "What should I do this week?" table on Snowflake, although it ran locally. | Streamlit in Snowflake uses an older Streamlit version than our laptops: `st.dataframe(hide_index=True)` and `st.line_chart(color=…)` do not exist there. | Tables use the variety as index instead of `hide_index`; the chart colour is optional. Checked by opening the deployed app. | Pin or check the runtime version of every managed service, and open the deployed app, not only the CI log. |
| 15 | On 3 Nov the **05:00 extraction never started**: GitHub silently skipped the scheduled run. At 06:30 the completeness gate failed the graph and GOLD stayed on the previous day. | GitHub cron is best effort; runs on the hour are often delayed or dropped under load. | Off-peak time (04:17), a fallback trigger at 05:47 that does nothing if the day already succeeded, and a `run-pipeline` workflow to re-run the graph by hand. | The safety net worked (no wrong figures), but a scheduler you do not control needs a fallback. |

## 2. What we would do differently with more time

1. **Run on the real cloud from day 1.** Most of our late surprises (items 2, 4, 5, 8) only appeared on Snowflake, not locally.
2. **Put the remaining Snowflake objects in Terraform** (stages, pipes, tasks are versioned SQL today). The Snowflake provider supports them; we kept SQL to go faster.
3. **Use real systems for the internal data**: the ERP, WMS and LIMS are simulated (on purpose, with known defects and an answer key). With a real ERP database we would use a managed CDC connector (Fivetran or Snowflake Openflow), see the TCO in docs/09.
4. **Calibrate the forecast on one real season.** The flow-index weights (50/30/20) and the 13-week demand baseline are assumptions. A seasonal baseline (Q4 gifting peak) is the next model improvement.
5. **Alert on stale external sources in the cockpit**, not only in the run log: during the Open-Meteo outage the decision was still computed, but without the weather signal.
6. **Measure the outcome**: compare, every month, the service level of the varieties we acted on with the ones we did not. That is the real proof of value.
